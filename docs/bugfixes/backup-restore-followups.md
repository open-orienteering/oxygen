# Backup and restore: follow-ups

Edge cases left out of the package 14 fix ([event-backup-restore.md](event-backup-restore.md)), with what a fix would take.

- **Restoring a copy beside its original.** The restore keeps the UUIDs, so restoring into the database that still holds the original stops on a duplicate key. Supporting it means remapping every UUID and the cross-references between tables (and inside JSON). The global serial ids are already renumbered.
- **Club graphics the layout draws.** The dump carries the event's own graphics; a template or sheet that draws a club graphic (`event_id` NULL) keeps its `graphicId`, which in another database names a different graphic or none. The venue checkout carries those (`src/sync/snapshotGraphics.ts`); the backup could too.
- **Very large dumps.** The restore reads the whole file into one string; a dump over about 512 MB (hex doubles the map blobs) fails with `ERR_STRING_TOO_LONG`. Splitting the file into sections while streaming would remove the limit.
- **A skipped GPS track is silent.** `restore-map-gps-tracks.sql` inserts `ON CONFLICT (id) DO NOTHING` without saying how many it skipped.
- **One transaction for the whole restore.** The five phases are separate transactions because the map, track and counter scripts each open their own. A failure after phase 1 leaves the event partly restored; the message says so and `--replace` starts over. Folding the scripts into the generated phase-1 script would make it atomic.
- **A restore button in the UI.** Restoring is a command-line step (`pnpm event:restore`, or `node packages/api/dist/cli/restore-event.js` in the image). An admin upload in the Event page would need the upload size limits, a progress report and the `--replace` confirmation.
- **Off-box copies of the automatic backups.** The venue `backup` service writes to a local directory; `BACKUP_DIR` can point at a USB stick, but nothing copies dumps to the cloud or checks that the stick is mounted. A dump into a missing mount point writes to the box's own disk.
- **Point-in-time recovery on the existing production instance.** `provision.sh` turns it on only when it creates the instance. The live instance needs the `gcloud sql instances patch` in [deploy-gcp-cloud-run.md](../ops/deploy-gcp-cloud-run.md) run once, between events (it restarts the instance). Not run from this change.
- **Compression.** The per-event dump is plain CSV text; the map blobs make it several megabytes. `Content-Encoding: gzip` on the route would cut that.
- **Schemas other than `oxygen`.** The dump, the restore and the map scripts name `oxygen.` explicitly; a `?schema=` other than `oxygen` in `DATABASE_URL` is ignored.
- **The cloud end of BLD-01 was not run.** The socket parsing is unit-tested with the `provision.sh` URL shape, and a dump against a closed port is tested to answer 502, but a download against Cloud SQL on Cloud Run has not been tried. Check it after the next deploy: Event page → Download backup, and the file ends with `-- BACKUP COMPLETE`.
- **The journal's shipping state on restore.** Journal rows keep `pushed_at` as dumped, and `journal_sync_state` is not restored, so on a venue box entries that were not shipped before the dump are shipped again after a restore. The cloud ingest is idempotent by entry id, which makes that safe, but a restore onto a box that holds no lease ships nothing until the event is checked out again.
