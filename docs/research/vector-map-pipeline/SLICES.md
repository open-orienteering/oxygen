# Sub-slice index

The work queue for the vector map pipeline, one row per unit a single
session implements end to end. Coordinator sessions read this file to
decide what is ready; implementer sessions update their own row. The
normative content lives in the spec chapters (`docs/map-*.md`), each of
which ends in a "Pending in this chapter" section — this index only
orders that backlog and records who is on what.

Branch model: `vector-map-pipeline` is the long-lived integration branch.
Every sub-slice is a worktree cut from it and a PR back into it. Spike
branches may be cut from it and merged back the same way. `main` is not
involved until a slice's gate (09 §4) has passed and the user decides.

## Status values

| Status | Meaning |
|--------|---------|
| `ready` | Dependencies merged; may be started |
| `blocked: <ids>` | Waits for the listed rows to merge |
| `in progress: <session>` | A session owns it; nobody else touches its area |
| `review` | PR open against `vector-map-pipeline` |
| `done <date>` | Merged; decision-log row written |
| `manual` | Needs the user (corpus, staging, the club's instance) |

A row is `done` only when all of: spec section written or updated,
"Pending in this chapter" trimmed, tests per AGENTS.md §4 matrix, a
decision-log row in [README.md](README.md) naming deviations, PR merged.

Two rows whose **area** columns overlap are never in progress at the
same time. Verification steps that use fixed ports or shared databases
(`pnpm test:e2e*`, `playwright test`, integration tests, the Docker
rebuild) run through `scripts/with-verify-lock.sh`; a hook blocks bare
invocations.

## Slice E — full migration: the flip and the retirement of the legacy pipeline (09 §4 E + F's retirement)

Split 2026-11-05 by the coordinator, on the user's direction the same day
(after testing slice D on prod, mobile included): **switch everything to
the new pipeline and remove the old one, without 09 §4's soak** ("one full
season event cycle", "no switch-backs for two releases") and without
keeping the two pipelines side by side for another slice. This slice
takes 09 §4 E (flip, tile jobs, env) **and** the retirement half of 09 §4
F (legacy editors, SVG/rsvg print, tables, base64 uploads,
`courses.geometry`). Slice F keeps only the editor's phase 2 (variations,
exchange, legs, 08 phase 2). Decision-log row "Slice E re-cut".

What the inventory found (coordinator's survey, 2026-11-05) that shapes
the order: the legacy pipeline is not a separable layer. The OCAD bytes in
`map_files.file_data` are parsed on paths every event takes —
`loadEventCrs` (course lengths, IOF/ppen export, control lat/lng, checks),
`loadEventMapObjects` (description autodetect, `suggestDescription`,
`DESCRIPTION_STALE`), `north_detection`, the club-map alignment of course
imports — and `course.mapMetadata` (the viewer's `documentHash`) returns
`null` unless the legacy render key resolves. Those readers move to the
document first (E1); only then can the bytes go. Silent fallbacks to the
legacy path exist for: no pinned document (tiles, rsvg print, legacy
editor), no WebGL2 / lost context (tiles), `CourseStackError` (rsvg print,
SVG course overlay), an unreadable document (OCAD cuts). Each gets a
non-legacy answer in E3 — an honest message, not a second renderer.

Release shape (no soak, one rollback boundary):

- **v0.6.0** = E1–E4c, E6: every event on the new
  pipeline, the switch and the legacy code gone, **columns and tables
  kept and still dual-written**, so `./deploy.sh v0.5.0` remains a working
  rollback.
- **v0.6.1** = E5: the drops. A release boundary, not a waiting period —
  it can follow as soon as the user has used v0.6.0 on prod.

Order: E0 (manual), E1 (api) and E2 (e2e) start at once — disjoint areas.
E3 after E1 and E2. Then E4a and E4b in parallel (disjoint); E4c and E6
after E4a (the SVG emitters' API consumers; `routers/course.ts`). E5 last.
E-pages (the templates redesign) waits for the user's design and blocks
nothing.

Decided in this split (coordinator, 2026-11-05; a row's planner may reopen
any of them with a reason; ★ = the coordinator's recommendation, taken
by the user's "go with recommendation" 2026-11-05, for user review):

- **No per-event switch after E3.** One migration sets every event
  `vector`; nothing reads `events.map_pipeline` or the three
  `map.*` settings afterwards (the column stays until E5 so v0.5.0 can
  still read it — and reads `vector`).
- ★ **Browsers without WebGL2 get no map**, the layer's existing "cannot
  draw the map" message (`data-status="webgl"`). Every phone and desktop
  browser the club uses has WebGL2 (B-gate, D-mobile). A lost context
  remounts the layer once, then shows the message.
- **A map without a pinned document** (import running, failed, or never
  backfilled) shows the import state — "map is being prepared" / the
  review link — not tiles. E0 makes it zero on prod before E3 ships.
- **`CourseStackError`** (a document whose colour stack is not aligned)
  becomes a visible error in print (400 with the reason) and in the
  viewer (course drawn on the GL layer's fallback colours, or a message —
  E3's planner chooses, E0 says whether any prod map hits it).
- ★ **Replay** (`components/replay/`, ~3,700 lines, mounted nowhere,
  built on tile URLs) is deleted in E4b; git keeps it for a future replay
  feature on the GL viewer.
- **Readers move to the document, not to `map_sources.bytes`**, wherever
  the document carries the data (CRS, north, objects, cuts); reading
  source bytes is the planner's fallback only where it does not, named in
  the spec. The OCAD reader (`ocad2geojson`) stays for import.
- **E2E on the new pipeline only.** Projects `map-legacy`, the
  `MAP_PIPELINE_SPECS` / `VECTOR_ONLY_SPECS` lists and the `mapPipeline`
  fixture go; the six dual-run specs run once in `chromium`; legacy-only
  specs and tests are deleted, not ported, where the new editor's specs
  already cover the behaviour.

### Answers (user 2026-11-07)

The rows above are written to these answers. Each keeps the question's
gist; 1, 2, 4, 5 and 6 took the planner's default, 3 did not.

1. **Corridor semantics** (F2; 08 §4.3 names `{ widthM, edge, whiteMm,
   whiteOpacity }` without defining them) — **the default**: `widthM` is
   the corridor's full width on the ground, inside which the map shows;
   `whiteMm` a white band that wide **outside** the corridor's edge
   (paper mm), beyond which the map shows again; `whiteOpacity` stored
   but drawn opaque until the backends carry alpha; `edge` draws the
   boundary in purple.
2. **Map exchange** (F5) — **the default**: control numbering continues
   across the exchange (08 §7's fixture said "restarts"); the exchange
   site is a control circle with its number on both parts; every part's
   description block carries the whole course.
3. **How a runner gets a variant** (F6b, F6c) — **not the default.** The
   planner proposed that the readout match the punches against every
   pooled variant and take the best one. The user: "I think it must be
   pre-set, if not someone could just follow another runner, not punch
   their own controls, and still get an accepted result. However, there
   is the issue of someone inadverntently getting the wrong map during a
   competition, so it would be nice if it was easy to see if they've
   actually run another fork successfully, and accept that, but that
   would be a manual step done at red exit." Taken as: variants are
   assigned to runners before the race (by hand per runner, or dealt per
   class; every runner in a pooled class has one — F6b); the readout
   validates against the runner's own variant only, so a run of another
   variant is a mispunch as any other; at the desk ("red exit" — in
   Oxygen the Runners page's expanded row and the readout-station page)
   the official sees plainly when the punches validate fully against
   another pooled variant, and which, and accepts it with one manual
   action that switches the runner's variant, is journaled and is never
   automatic (F6c). The split's deviation (3) — the readout picking a
   variant — is withdrawn (README decision log, "Slice F answers").
4. **The all-variations print** (F8) — **the default**: Export ▾ *All
   variations* prints each sheet once with every alternative in the one
   purple, for officials; the runners' maps are the per-variant pages.
5. **Empty alternatives** (F6 / F7) — **the default**: alternatives may
   be empty (not all of them), so *Create variation here* saves at once
   and a variant without the group's controls is a straight leg.
6. **Consolidation F12** — **the default**: in this slice, as the last
   row.

Decided by the F0 planner from answer 3 and the code survey, each for
user review (the F6b / F6c planners may reopen with a reason):

- **Every runner in a pooled class has a variant**, assigned at creation
  (the least-populated variant) — late entries at the event and Eventor
  imports included — and re-dealt in start order by *Distribute
  variants* after the draw. Alternative: leave late entries unassigned
  and warn; rejected because an unassigned runner would be matched
  against the root's first-alternatives path, which is no variant.
- **The draw does not deal variants itself** in F6b: the Classes page's
  *Distribute variants* is run after the draw. A checkbox on the draw
  panel (`DrawPanel.tsx`, `draw.execute`) is one call away and is a
  polish row if the user wants it.
- **The accept lives at the desk, not on the kiosk**: the kiosk is the
  runner's screen and shows MP with one line pointing to the desk.
- **Only a full match is offered**: a variant the punches validate
  against with no required control missing. A near-miss on another
  variant is an ordinary mispunch for the official to judge with the
  punch table, as today.
- **No per-runner map page** (the runner's name on the map): F8 prints a
  per-variant stack sized by the assigned runners (`copies=runners`);
  naming maps is a separate feature if wanted.
- **The Classes page's "forked courses" multi-select stays as it is**
  (it saves only its first pick): with F6 a class picks the root and the
  pool is the root's variants; a cleanup of that control is not F's.
