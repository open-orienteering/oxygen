| 2026-11-17 | Slice I split (I1–I7, I-gate; I0) | **Planned by the coordinator as the I0 planner (Fable) — the smaller decisions for user review**, recorded in `SLICES.md` "Slice I" → "Decided in this split" and `map-symbols.md` §9.3: the unit that takes a place in the IOF order is a colour *use* (one colour reference of one symbol), so a source colour serving several palette rows is split into several stack rows; a use's role comes from the matched or suggested library entry, then a rule on class, percent, kind and part; `header.colours` stays "index = draw order"; source order stays the rule for mask whites, graphic objects' colours and uses with no role; today's alignment (§9.2, C15 included) is kept whole as the `source` order; one importer bump in I5; the harness (I1) first. | The 2026-11-14 experiment: a permutation of the table is wrong on about half the maps (one colour, several IOF rows on 8 of 10; masks; layout artwork; deliberate deviations), while identification is not the obstacle (≤ 0.21 % of colour uses without a palette entry). (3) The review page shows nothing about colours today, and the switch and the lists need a place. |

| 2026-11-17 | I2 roles: interface and rule table | **Decided by the I2 session** (`map-symbols.md` §9.3 "Roles"): `roleOfUse(use, infos, symbol, palette)` takes every source colour's info (a rule reads the classes of the symbol's other colours: the infill under a road outline, the fill under cultivated dots) and a `RolePalette` built once per document (the spec's own rows; the class of every alignment-palette row, so `orange-skio` resolves on iof2022), not one colour's info and a palette as the row wrote. 14 parts: hatch, text shadow and text frame added because the IR has them and every reference must be a use. The kind is `render.type`. A path is an array of keys and indices (`renderColourPaths`, `mapRenderColourRefs` in `render/transform.ts`; `ColourPath`, since `RenderPath` is taken by the pass stream). The table is per spec with candidates chosen by same class and nearest percent. Black road outline also covers a halo under a brown-screen main (Mapper's combined roads) and an area border round a brown-screen fill (ISOM 501). Screens go by percent whatever the part. The rule reads neither the colour's name nor §9.1's `paletteId` (ski rows aside). `alternatives[]` are not hints. | The table reproduces the library's own row for 203 / 249 ISOM and 183 / 226 ISSprOM uses with no match, on both editions; the rest are whites and purples (hint only) and six named uses, pinned in the test. With each entry as its own hint every use reproduces. |
| 2026-11-17 | I2 roles: cultivated dots, ski colours, symbols drawn inside out (Q1–Q3) | **Decided overnight on the user's standing instruction (2026-11-17), for review** — the I2 planner's recommendations. (Q1) `black-cultivated` only for a disc-only pattern on an area whose fill is yellow; any other black 100 % dot pattern is `black100` (narrows the row's "an area's dot pattern"). (Q2) A colour §9.1 identifies as `green-skio` or `orange-skio` takes that role for every use, after the hint; `white-skio` stays hint-only like every white. (Q3) I2 rules only the road case (outline or halo round a brown-screen infill → `black-road-outline`, under the infill); the general hazard — a symbol's under-part ranked above its over-part, e.g. a black halo under a blue main — is recorded in §9.3 as row I4's, to be fixed against the I1 harness. | (Q1) The library draws stony ground (ISOM 208–212) as black 100 % dots, and `black-cultivated` ranks under the greens: an unmatched stony ground would vanish; with the yellow condition every black pattern in the library reproduces. (Q2) The ski inks are identified per colour by name or position (§9.1, never aliased, §9.2 step 3); by the table a ski green would sink under black as `green100-point` and the orange get no role. (Q3) Which side moves is a corpus question, the kind I4 fixes against the harness; the source order never had it. |
