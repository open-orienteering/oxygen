# Area 01 review: API routers, authentication and authorisation

Scope: the tRPC routers and REST routes under `packages/api/src` (procedure builders in `trpc.ts`, `auth.ts`, `permissions.ts`, `restGuard.ts`, the venue forwarder, every router file and route handler), reviewed on `main` at commit `df5460c3`, plus the API part of the unmerged PR #254 (branch `claude/project-thread-avzbks`). Two Fable reviewers read the area in full, split between them; every finding then went to an independent Fable verifier (one per finding or small group) that had not seen the reviewer's reasoning and was asked to disprove it. Reproductions ran against a throwaway Postgres on :5433 (`oxygen_test`) through `scripts/with-verify-lock.sh`, or as standalone scratch scripts; no repository code was changed.

Severity is judged per deployment mode. `AUTH_MODE=off` is the documented default on a LAN venue box and opens every gate by design, so pure authorisation findings are rated for `AUTH_MODE=proxy` (cloud). Findings that lose or corrupt data are rated for all modes.

Fix first:

1. **API-01 and API-03 together (B-01, B-02):** the journal sink `events.push` accepts every race and reference write from any signed-in user with no capability check, and its reference upserts can rewrite another competition's rows; on a proxy-mode cloud any member can wipe any event mid-race.
2. **API-02 (B-03):** `events.push` ignores the entry's own `competitionId`, so an outbox drain that straddles a navigation applies event A's readouts and registrations to event B, journals them there, and A can never receive them.
3. **API-04 and API-10 (B-07, B-08):** one press of "Sync from Eventor" on race day can flip every pre-entered runner, including those already read out, to Cancelled, and the next sync brings them back as `unknown` with their status lost.

Dominant theme. The area's procedure builders are sound, but two surfaces sit outside them. The first is the journal sink: `events.push` is a bare `eventProcedure` (documented as such in `docs/system/authentication.md:231`) and applies runner, result, course, control and class writes that are otherwise gated by `race.operate`, `event.manage` or `courses.edit`, without checking capability, the entry's competition, or which event an addressed row belongs to. The second is `publicProcedure`: a router-wide sweep run during verification found 26 of 326 procedures that reach input validation or the handler with no identity in proxy mode, including the Eventor directory (personal data of every runner), `testLab.generateEvent` and `lease.checkout`. On an `AUTH_MODE=off` venue box none of the authorisation findings adds exposure, because every LAN device already holds every capability. Such a box is still exposed to every data-integrity finding below (journal replay of the wrong competition or wrong status, the non-transactional course import, Eventor mass-cancel, Test Lab overwriting a live event, re-checkout deleting un-shipped entries, duplicate radio punches), to the two-request upload memory blow-up (API-23) from any LAN device, and to a LAN device checking out any event of the cloud it is paired with (API-25).

## Findings

### API-01 `events.push` applies every journaled write with no capability check (proxy mode)
- Was: B-01 (also reviewer A out-of-scope sighting 2) · Area: API routers and auth · Category: security
- Severity: critical in `AUTH_MODE=proxy`; no effect in `off`, where every caller already has all capabilities.
- Location: `packages/api/src/routers/events.ts:229` (procedure), apply switch `packages/api/src/routers/events.ts:345-798`; root `packages/api/src/trpc.ts:164` (`eventProcedure = authedProcedure.use(requireEvent)`); documented at `docs/system/authentication.md:231`.
- What is wrong: `push` calls `ingestJournalEntries(ctx.db, ctx.event, input.events)` and nothing else; neither it nor `applyEvent` reads `ctx.user` or capabilities. The same writes through their own procedures are gated: `runner.create/update/delete` are `manageRaceProcedure` (`runner.ts:417/509/588`), `cardReadout.applyResult` is `raceOperateRaceProcedure` (`cardReadout.ts:805`), `course.importCourses` is `coursesEditRaceProcedure` (`course.ts:1780`). `AUTH_AUTO_PROVISION` (`auth.ts:66,128-141`, set on the Cloud Run deploy) creates a grant-less member for anyone the proxy admits.
- Scenario: proxy mode, user U is a plain member with no grant on event `sm-2026`. U sends `events.push` with `x-competition-id: sm-2026` and entries `runner.deleted {runnerId: 1..2000}` (resolved by seq, `events.ts:285-311`), or `result.applied {...status: 4}`, or `reference.imported {replaceAll: true, courses: [], controls: []}`. Every runner is soft-deleted, results are overwritten, or every course and control is removed and every class loses its course (`events.ts:694-722`). Each equivalent direct procedure would answer FORBIDDEN.
- Fix (M): in `push`, resolve `capabilitiesForContext(ctx)` once and require a capability per entry type before applying: `card.read`, `finish.*`, `start.*`, `result.applied`, `punch.*` need `race.operate`; `runner.registered|updated|deleted` need `race.operate` or `event.manage` (owner decision: registration desks queue `runner.*` through the outbox, and mapping them to `event.manage` only would strand race-crew desks); `class.upserted` needs `event.manage`; `course.upserted`, `control.upserted`, `reference.imported` need `courses.edit`. Unknown types default to deny; an empty `events` array stays allowed (the client reads `serverTimeMs`). Refused entries go to `failed` with a FORBIDDEN code. Caveats from verification: (1) venue-to-cloud shipping calls this same procedure (`sync/shipper.ts:79-110`) with `x-oxygen-sync-secret` and, behind IAP, a service-account token that resolves to a grant-less member, so a valid sync secret (`ctx.syncSecret === syncSharedSecret()`, already in context at `trpc.ts:59`) must bypass the capability map, or shipping moves to a `peerProcedure` variant; decide whether peer push still needs `ctx.user`. (2) Station outboxes mark a failed entry `failed` (`packages/web/src/lib/offline/sync.ts:35,52-61`) and stop retrying, so the map must match what the UI lets each role enqueue, or FORBIDDEN entries strand race data on the device. (3) Check whether station drains can reach the cloud through `sync/venueForwarder.ts`, where they would be checked as the human. Fix API-03 in the same change. Change `docs/system/authentication.md:231`. Tests: see API-37.
- Verification: Confirmed (from code: `events.ts:229`, `trpc.ts:164`, apply paths `events.ts:566-575`, `:390-415`, `:694-722`; `events-push.test.ts` has no auth assertion).

### API-02 `events.push` ignores the entry's `competitionId` and keys idempotency by bare id: offline entries land permanently in the wrong competition
- Was: B-03 · Area: API routers and auth · Category: functional (competition mix-up)
- Severity: high, all modes.
- Location: `packages/api/src/routers/events.ts:69` (field accepted), `packages/api/src/routers/events.ts:88-151` (`ingestJournalEntries` never reads it), `packages/api/src/routers/events.ts:99-106` (idempotency lookup by `id` only), `packages/api/prisma/schema.prisma:1064` (`JournalEntry.id` global primary key); client `packages/web/src/lib/trpc.ts:22-31,65-77`, `packages/web/src/lib/offline/sync.ts:14-68`, `packages/web/src/hooks/useEventQueue.ts:51-75`.
- What is wrong: each wire entry carries the `nameId` it was recorded for, but the server applies it to `ctx.event` from the header. The web client computes `x-competition-id` from `window.location.pathname` when each request is dispatched, while the module-level drain loop keeps sending 50-entry batches after navigation (the hook's `cancelled` flag only suppresses state updates). Once an entry is journaled under the wrong event, a later push with the right header is answered `synced` by the id-only idempotency check, so the right event never gets it.
- Scenario: a station regains network with 300 pending entries for `/eventA`. One batch is slow (slow uplink is exactly when a backlog exists) and the operator goes A, selector, B (or uses browser back/forward between two event URLs). The next batch is sent with header `eventB`: `card.read` is stored for B, race-state entries resolve a B runner by card number or seq and get A's finish and status, `runner.registered` creates a runner in B if B has a class with the same seq. The server returns them as `synced`, the client drops them from the outbox, and they are shipped to peers as B entries. If a batch is dispatched while the URL is `/`, `/settings` or `/admin`, no header is sent and the loop breaks harmlessly.
- Fix (S server, M with client): in `ingestJournalEntries`, before the idempotency lookup, `if (entry.competitionId !== event.nameId) { failed.push({ id, error: "COMPETITION_MISMATCH" }); continue; }` (the schema requires the field, so a strict check is possible). Make the idempotency lookup event-aware: select `eventId` and treat a hit under another event as a failure, not `synced`. Node-to-node paths already send the same `nameId` on both sides (`events.ts:213`, `sync/shipper.ts:83-112,204,234-240`, `routers/lease.ts:142-166`); no slug-rename path was found, but if one exists the check would strand entries, so the client must keep mismatches retryable. Client (web area): send an explicit per-batch header taken from the entries' own `competitionId` instead of the URL, which removes the race and lets A's backlog drain while the operator is elsewhere; have `sync.ts` treat a mismatch as `pending`. The unfiltered `drainEventQueue(undefined)` path is unreachable today (single caller `SyncStatusIndicator.tsx:161`) but would push every competition under one header; the server check closes it. Existing tests already send matching slugs (`events-push.test.ts:49`, `course-variants.test.ts:228,469`, `lease.test.ts:349`, `runner-variants.test.ts:227,266,415`, `e2e/offline.spec.ts:312`, `e2e/lease.spec.ts:84`). Add: entry with `competitionId: "other"` is in `failed` and nothing is applied; an entry already journaled under event B is not reported `synced` for event A.
- Verification: Confirmed (from code: `events.ts:69`, `:99-108`; client loop and header derivation read in full). The navigation timing was not reproduced in a browser.

### API-03 Journal reference upserts address rows by bare UUID and pass client `fields` to Prisma: cross-event write, mass assignment, non-atomic child replace
- Was: B-02 (the adjacent hole the B-01 verifier also found) · Area: API routers and auth · Category: security
- Severity: high. Proxy mode: becomes the remaining cross-competition hole once API-01 is fixed. All modes: the non-atomic child replace on its own.
- Location: `packages/api/src/routers/events.ts:843-915` (`applyReferenceUpsert`): control `:866-870`, course `:875-881`, class `:898-904`; payload schema `packages/api/src/routers/events.ts:76`; also reached per row from `reference.imported` at `packages/api/src/routers/events.ts:691-702`.
- What is wrong: `db.control.upsert({ where: { id: payload.id }, create, update: fields })` (same for course and class) never checks that an existing row belongs to `eventId`. `fields` is the raw `z.record(z.string(), z.unknown())` payload, so any column is writable, including `eventId`, `seq`, `id`, `removed`, `parentCourseId`, `finishControlId`, class `courseId`. `courseControl.deleteMany({ where: { courseId } })` and `classCoursePool.deleteMany` are unscoped, child `controlId`/`courseId` are not checked against the event, and upsert, delete and recreate are separate statements. `seq` from the payload is honoured on create, so a crafted entry can also squat an `(eventId, seq)` slot.
- Scenario (all reproduced): a caller bound to event A pushes `course.upserted {id: <B's course>, seq: 0, fields: {removed: true}, courseControls: []}`: B's course is removed and its `course_controls` rows deleted. `fields: {eventId: <A's id>}` moves B's course into A. `courseControls: [{position: 0, controlId: <nonexistent>}]` on an existing course reports the entry `failed` after its old `course_controls` were already deleted, leaving a course with no controls that nothing repairs. A new course in A can link a control of B.
- Fix (M): at the top of `applyReferenceUpsert`, load the row by id; if it exists with `eventId !== eventId` throw "row belongs to another event"; if it does not exist, create under the local `eventId` (bigint ids differ per node, UUIDs are shared, so this is the right test). Strip `id`, `eventId`, `seq`, `createdAt`, `updatedAt` from `fields` and whitelist against what `portableFields` in `referenceJournal.ts` emits (that set still includes `version`, `removed`, `parentCourseId`, `variantKey`, `finishControlId`, class `courseId`, `structure`). Check that FK-valued fields and every `courseControls[].controlId` / `coursePools[].courseId` belong to the event. Decide how unknown keys are handled across peer versions (today they fail Prisma validation; dropping them silently is a behaviour change; consult `sync/dropped-columns.ts`) and document it. Wrap upsert plus child replace in one `$transaction`, threading a `Prisma.TransactionClient` (as `referenceJournal.ts` does with its `Db` union); note the whole `reference.imported` apply is also non-transactional and needs the same wrapper to avoid a half-applied import. Regression net: `course-variants`, `course-structure`, `journal-completeness` integration tests round-trip real payloads through `ingestJournalEntries`. Add the four reproductions as tests.
- Verification: Confirmed (reproduced: throwaway integration test against `oxygen_test`, 4/4 assertions passed).

### API-04 `eventor.sync` cancels every runner missing from Eventor's entry list, with no guard for an odd response or for runners who already have a result
- Was: B-07 · Area: API routers and auth (overlaps Eventor) · Category: functional
- Severity: high, all modes; arguably critical (one unconfirmed button press, mid-event, unrecoverable in-app).
- Location: `packages/api/src/routers/eventor.ts:1183-1199` (cancel loop), `packages/api/src/routers/eventor.ts:1016-1023` and `:1092-1096` (reinstate), `packages/api/src/eventor.ts:699-701` (`fetchEntries` returns `[]`); in-app help `packages/web/src/i18n/locales/en/event.json:137`; only caller `packages/web/src/pages/EventPage.tsx:352,399`.
- What is wrong: step 5 sets `status = cancel` for every Eventor-linked runner whose person id is not in `seen`, whatever its status or finish time. The in-app help promises the opposite ("Runners who disappear from Eventor and have no race result are automatically marked as Cancelled"). `eventorFetch` throws only on non-2xx; `fetchEntries` returns `[]` for `<EntryList/>`, an HTML maintenance page, an empty body or `<Error>` (reproduced with the repo's parser). Reinstate sets `unknown`/`no_timing` when Eventor has no result (always, on race day), so the original status is not restored. No transaction; nothing is journaled.
- Scenario: race day, the operator presses Sync; Eventor answers 200 with a body lacking `EntryList`. All pre-entered runners, including those read out as OK/MP/DNF, become Cancelled: they stay in `lists.resultList` but with status 21, place 0 and no running time, drop out of participant and club counts, and LiveResults publishes them as DNS (`liveresults.ts:65`). The next good sync sets them all to `unknown`: LiveResults shows MP/DNF runners as OK (`liveresults.ts:67`) and in-app lists leave every runner, OK ones included, unplaced. Per runner, any entry withdrawn or moved in Eventor after the race loses its result the same way with no odd response.
- Fix (S): (1) before any write (including `syncClassesFromEventor` / `syncClubsFromEntries`), abort with PRECONDITION_FAILED when `entries.length === 0 && existing.length > 0`; a percentage threshold needs an override flag and a confirm in `EventPage.tsx`, since small events can lose over 20 % genuinely. Better, make `fetchEntries`, `fetchResults` and `fetchEventClasses` throw when the root element is missing (today a missing `ResultList` or `EventClassList` is also a silent `[]`). (2) In the cancel loop skip runners with `finishTime !== 0`, a finished status, `dns`, or a card readout row. (3) Reinstate only when `finishTime === 0`; runners already damaged (cancel with finish time) stay cancelled unless status is recomputed from the card. (4) Filter `existing` (`:958-962`) by `removed: false`. Adjust `__tests__/integration/eventor-reentry.test.ts:333`, which mocks exactly the empty case; add "entries empty while runners have results" and "withdrawn runner with a result keeps its status". Fix API-10 in the same change.
- Verification: Confirmed (from code, plus parser behaviour reproduced with a scratch script). Whether real Eventor returns 200 with a non-EntryList body is external and unproven; the per-runner case needs no odd response.

### API-05 `course.importCourses` with `replaceAll` wipes all courses, controls and class links before a non-transactional rewrite
- Was: B-06 · Area: API routers and auth · Category: stability
- Severity: high, all modes.
- Location: `packages/api/src/routers/course.ts:1883-1899` (wipe), writes `packages/api/src/routers/course.ts:1901-2294`, journal `packages/api/src/routers/course.ts:2341`; comment `:2296-2303`; doc `docs/system/offline-architecture.md:180-184`; dialog default `packages/web/src/components/CourseImportDialog.tsx:30`.
- What is wrong: the wipe is three auto-committed `updateMany` calls; hundreds of per-control and per-course statements follow on the root client. The code comment and the doc reason only about a crash between a completed import and the journal append, not about a failure between wipe and end of writes. `replaceAll` defaults to true in the UI, so this is every import. `persistStructure`'s own contract says "call inside the write transaction".
- Scenario: race morning, the setter re-imports a corrected course file. The wipe commits; then `allocateStartFinishCode` throws `START_FINISH_CODES_EXHAUSTED` (`control.ts:397-401`), a concurrent `control.create` causes a P2002 on the unlocked `max+1` seq (`course.ts:1955-1957`), a `findUniqueOrThrow` in `syncVariants`/`syncClassPool` fails, the DB connection drops, or the API restarts. The event has no active course or control and no class has a course, so readout finds no course for any runner (`cardReadout.ts:196,633`); no `reference.imported` entry exists, so a peer still has the old state. Re-running the import normally repairs it. Without `replaceAll` the same non-atomicity can leave one course with its `course_controls` deleted.
- Fix (M): run wipe through class assignment, version stamping, `appendJournal` and `emitVariantSync` (`:1883-2360`) in one `ctx.db.$transaction(async (tx) => ..., { timeout: 120_000, maxWait: 10_000 })`, passing `tx` everywhere; the nested `$transaction` calls at `:2066` and `:2094` become direct calls on `tx`. All named helpers already take a transaction client (signatures checked; bodies not all read for a hidden global client). Keep parsing, alignment, OCAD CRS load and the held-code pre-check (`:1800-1881`) outside. The explicit timeout is mandatory (Prisma default 5 s); measure with a large file. `allocateStartFinishCode`'s `pg_advisory_xact_lock` will then be held for the whole import, blocking concurrent `control.create` for its duration. Update the comment at `:2296-2303` and `offline-architecture.md:180-184`. Test: inject a failure after the wipe and assert courses, controls and class links are unchanged and no `reference.imported` row exists.
- Verification: Confirmed (from code; no failure injected).

- Was: A-03 · Area: API routers and auth · Category: stability (data loss)
- Severity: high, all modes (`event.manage` in proxy mode, anyone in `off`).

Update `__tests__/integration/testlab.test.ts` (`createTestEvent` needs the flag; `:244-260` pins unguarded `clearRunners`), `shell-tabs.test.ts` expectations, and `docs/screenshots/capture.ts`. Minor, same file: the 500 ms `setInterval(tick)` (`testLab.ts:509-540`) lets async ticks overlap and skip a readout (test-only impact).

### API-07 `lease.checkout` deletes a local event copy that still has un-shipped journal entries

Show the pending count in `VenueLeasePanel` when no lease is held. If `journalSyncState.upsert` or local `acquireLease` fails after the import (`lease.ts:172-189`), the catch releases the cloud lease but the local copy is already replaced; consider ordering. Keep `lease.test.ts:828-857` (re-checkout after a clean checkin) passing; add "re-checkout with a pending entry is refused and deletes nothing". Correct `sync/lease.ts:297-300` and `offline-architecture.md:248` to describe the enforced barrier.

### API-09 `result.applied` replay maps only OK/MP/DNF; every other status becomes `unknown`
